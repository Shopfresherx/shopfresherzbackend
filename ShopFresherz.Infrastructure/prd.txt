1. Executive Summary
ShopFresher'z is an e-commerce platform for gadgets and electronics. The uploaded screens show two connected products: a customer storefront and a separate admin console. The backend must support catalog management, product variants, inventory, cart, checkout, payments, order tracking, coupons, flash deals, reviews, customer dashboards, loyalty points, referrals, notifications, analytics, and content management.
The backend should be built as a versioned API with a relational data model, transactional order creation, payment webhooks, inventory reservation, admin role controls, and clear audit logs. The UI already expects a rich admin experience, so the backend cannot be a simple CRUD layer. It must enforce business rules consistently and protect money, inventory, and customer data.

Goals
Reliable buying flow: Customers can browse products, manage cart and wishlist, complete checkout, pay, receive confirmation, and track orders.
Admin operational control: Admins can manage products, categories, inventory, content, coupons, flash deals, customers, orders, reviews, settings, and analytics.
Data integrity: Product price, discount, tax, shipping, coupon, loyalty, inventory, and payment states are stored as immutable order snapshots when checkout is completed.
Secure foundation: Use RBAC, rate limiting, audit logs, webhook verification, tokenized payment references, and strict validation.
Scale-ready architecture: Use async jobs for emails, notifications, analytics aggregation, image processing, coupon expiry, low stock alerts, and order lifecycle updates.

Non-goals for v1
Full marketplace seller onboarding is not shown in the screens and should not be built unless confirmed.
Warehouse robotics, real-time carrier API routing, and multi-warehouse allocation are outside v1 unless logistics integrations are confirmed.
Storing raw card numbers is strictly out of scope. Saved cards must use payment gateway tokens or authorization references only.
Complex returns and refunds are not visibly shown. Basic cancel/refund hooks can be prepared, but policy must be confirmed before implementation.

C#/.NET implementation requirements
Project structure: Use an ASP.NET Core Web API solution with clear projects such as Api, Application, Domain, Infrastructure, and Tests. Keep controllers thin and move business rules into services/use cases.
Data access: Use Entity Framework Core with SQL Server provider, code-first migrations, DbContext per bounded application, explicit indexes, unique constraints, and transaction scopes for checkout/order/payment flows.
Authentication: Use ASP.NET Core Identity or a custom identity layer with JWT access tokens, refresh tokens, email verification, password reset, role claims, and policy-based authorization.
Validation: Use request DTOs plus FluentValidation or DataAnnotations. Never bind EF entities directly from public API requests.
API contract: Expose Swagger/OpenAPI for every endpoint. Version all public APIs under /api/v1 and keep response envelopes consistent.
Background processing: Use Hangfire, Quartz.NET, or hosted workers for emails, webhook retries, stock alerts, image processing, invoice generation, scheduled coupon expiry, and analytics rollups.
Configuration and secrets: Use appsettings by environment, environment variables, and a secret manager. Do not commit connection strings, Paystack keys, SMTP passwords, or JWT signing secrets.
Logging and observability: Use ILogger/Serilog-style structured logs, correlation IDs, health checks, metrics, and alerts for checkout, payment webhooks, order creation, SQL Server errors, and background job failures.

4. Backend Architecture Requirements

High-level architecture
The backend should be a modular monolith for v1, with clean domain boundaries and versioned APIs. This is faster and safer than starting with many microservices. Keep modules separated at the app/package level so the system can later split payments, search, notifications, or analytics into services if traffic demands it.

Client Web/Mobile
-> API Gateway / Load Balancer
-> Backend API /api/v1
-> Auth Module
-> Catalog Module
-> Cart and Checkout Module
-> Payment Module
-> Order Module
-> Admin Module
-> Notification Module
-> Analytics Module
-> Microsoft SQL Server
-> Redis Cache plus Hangfire/Worker Queue
-> Object Storage for media
-> Paystack Webhook Receiver
-> Email/SMS Provider
-> Observability Stack

Backend principles
Transactional order creation: Creating an order, reserving inventory, applying coupon redemption, and creating payment intent must be atomic where possible.
Immutable order snapshots: Order items must store product name, SKU, image, selected variant, unit price, discount, tax, and shipping at purchase time. Later product edits must not rewrite old orders.
Payment source of truth: Payment status should only become paid after gateway verification or webhook confirmation. Never trust client-side success alone.
Idempotency: Checkout, payment initialization, webhook processing, and status updates must be idempotent to prevent double charges, duplicate orders, or duplicate points.
Audit everything sensitive: Price changes, stock changes, coupon creation, order cancellation, status updates, admin login, role changes, and setting changes must write audit records.
Queue slow work: Email, SMS, image resizing, analytics aggregation, low stock scanning, and notification fan-out must run async.

-----------+-----------------------------------------------------------------------------------+-------------------------------------------------

5. Roles, Permissions, and Security Model

Roles

Role              | Allowed                                                                                               | Restricted
------------------+-------------------------------------------------------------------------------------------------------+---------------------------------------------------------------------------------------------------
super_admin       | Full access, role management, payment settings, site settings, all admin modules.                     | Cannot directly mark payment as paid without gateway evidence unless emergency override is logged.
admin             | Catalog, content, orders, reviews, customers, analytics.                                              | Cannot manage roles or payment secrets.
ops_manager       | Orders, shipments, tracking, inventory view, status changes, cancellation workflow.                   | Cannot edit product pricing unless granted.
catalog_manager   | Products, categories, inventory, media, SEO.                                                          | Cannot view payment secrets or customer full payment records.
marketing_manager | Coupons, flash deals, banners, featured products, referral and loyalty rules.                         | Cannot cancel paid orders or change payment settings.
support_agent     | Read customer profiles and orders, respond to customer issues, limited notes.                         | Cannot edit prices, inventory, coupons, or payment settings.
customer          | Own account, cart, wishlist, orders, addresses, reviews, loyalty, referrals.                          | Cannot access any admin endpoint or another customer account.
guest             | Browse catalog, create guest cart, checkout, public tracking with reference and contact verification. | Cannot access account dashboard or saved data.

Security requirements
All admin APIs require authenticated user, admin role, permission check, CSRF protection if using cookie sessions, and audit logging.
Customer APIs require ownership checks on cart, wishlist, addresses, payment method tokens, orders, reviews, and notification records.
Use JWT with refresh tokens or secure server-side sessions. Refresh tokens must be rotatable and revocable.
Use rate limits on login, register, password reset, email verification, coupon validation, tracking lookup, and checkout attempts.
Use input validation on every request. Normalize email, phone, SKU, slugs, and money amounts. Reject negative pricing and invalid stock quantities.
Use Paystack webhook signature verification. Process webhooks idempotently by event id and payment reference.
Never store raw card PAN, CVV, or expiry as a payment instrument. Store only gateway customer code, authorization code, card brand, last4, and expiry month/year if provided by the gateway.
Money must be stored as integer minor units, such as kobo, not floating-point decimals.
Protect media uploads with file type checks, size limits, malware scanning when available, and private original storage with public optimized derivatives.
Use soft delete for products, categories, coupons, customers, and CMS content where historical orders need references.

6. Core Domain Modules

6.1 Authentication and Accounts
Register with first name, last name, email, phone, and password.
Send email verification code or token after registration.
Block sensitive actions until email is verified if business decides this is required.
Support sign in, forgot password, reset password, logout, and refresh session.
Store password with strong hashing such as Argon2id or bcrypt.
Support guest checkout without forcing registration, while allowing account linking later by email or phone.

Acceptance scenario | Expected backend behavior
--------------------+-----------------------------------------------------------------------------
Register success    | A new customer receives verification email and can sign in if policy allows.
Reset password      | Token expires, is single-use, and does not reveal whether an email exists.
Admin login         | Admin login writes audit event and uses stronger rate limit rules.

6.2 Catalog and Product Management
Admin can create product with name, description, category, price, compare-at price, stock quantity, SKU, images, SEO meta title, SEO meta description, slug, active flag, and featured flag.
Support product status values: draft, active, inactive, out_of_stock, archived.
Support variants/options shown in product detail such as color, memory, storage, and size.
Support product gallery images with sort order and primary image.
Support brand, category, availability, rating summary, and product tags for storefront filters.
Generate unique slug from name but allow admin override if unique.

Acceptance scenario | Expected backend behavior
--------------------+------------------------------------------------------------------------------------------------------------------
SKU uniqueness      | The API rejects duplicate SKU for active or draft product variants.
Price validation    | Compare-at price must be greater than or equal to selling price when present.
Product detail      | Customer endpoint returns product, variants, media, rating summary, stock status, related sections, and SEO data.

6.3 Categories and Navigation
Admin can create, update, activate, deactivate, and reorder categories.
Categories support optional parent category, icon/image, slug, menu visibility, and featured flag.
Customer storefront can fetch category menu, top categories, and category detail page.
Category deletion must be blocked if active products exist unless reassignment or archive is selected.

Acceptance scenario | Expected backend behavior
--------------------+------------------------------------------------------------------------------
Menu API            | Header category dropdown loads active visible categories in configured order.
SEO                 | Category pages return slug, meta title, and meta description.

6.4 Inventory
Store stock on hand, reserved stock, available stock, low stock threshold, and stock status per product or variant.
Checkout must reserve stock before payment finalization to reduce overselling.
Release reservation when payment fails, expires, or order is cancelled before fulfillment.
Deduct stock only when payment is confirmed or when order is moved into processing, depending on policy.
Low stock alerts trigger admin notifications and dashboard cards.

Acceptance scenario | Expected backend behavior
--------------------+------------------------------------------------------------------------------------------------------
Oversell protection | Two simultaneous checkouts cannot push available stock below zero.
Adjustment log      | Every manual stock change records before quantity, after quantity, reason, admin user, and timestamp.

6.5 Pricing, Tax, Shipping, Coupons, and Flash Deals
Price calculation service must combine product price, active flash deal, coupon, shipping fee, VAT/tax, and loyalty redemption if enabled.
Coupons support code, type, value, min order amount, max discount, usage limit, per-user limit, start date, end date, active flag, eligible categories/products, and first-order-only flag.
Flash deals support title, banner image, start time, end time, active flag, product list, deal price or percent discount, and stock limit if needed.
Tax should be configurable. Screenshot shows VAT at 7.5 percent in admin order detail, so default tax assumption is 7.5 percent until confirmed.
Shipping methods should be configurable by name, price, ETA, free shipping threshold, region, and active flag.

Acceptance scenario | Expected backend behavior
--------------------+----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
Coupon expiry       | Expired coupon cannot be applied and scheduled jobs mark it expired.
Best discount rule  | If a product has flash deal and coupon, backend applies configured stacking rule. Default: coupons cannot discount already flash-deal-discounted items unless explicitly allowed.
Quote consistency   | Checkout quote and final order totals must match unless cart changed, coupon expired, or stock changed.

6.6 Cart, Wishlist, and Checkout
Cart supports guest and logged-in users. Guest cart uses secure anonymous cart id or session key.
Cart item stores product, variant, quantity, selected options, price preview, and validation state.
Wishlist belongs to registered customer. Guest wishlist can be local-only unless account creation is implemented.
Checkout supports billing information, delivery/shipping selection, payment method selection, order summary, and place order.
Registered checkout can save address and use saved addresses. Guest checkout stores address snapshot only.

Acceptance scenario | Expected backend behavior
--------------------+-------------------------------------------------------------------------------------------------------
Cart validation     | Cart returns unavailable, price_changed, stock_changed, and coupon_invalid flags when needed.
Guest checkout      | Guest can place order with email and phone and later track using order number plus verification field.
Registered checkout | Logged-in customer order appears in dashboard order history immediately after creation.

6.7 Payments
Use server-side payment initialization with Paystack. Client receives payment authorization URL or access code from backend.
Create Payment row before redirecting to gateway. Use unique reference generated by backend.
Payment becomes paid only after webhook or server verification confirms success.
Handle failed, abandoned, pending, reversed, refunded, and chargeback states if Paystack supplies them.
Saved card feature must use Paystack authorization reference. Do not store raw card numbers.
Admin order detail can display gateway name, payment status, amount, reference, and paid timestamp.

Acceptance scenario | Expected backend behavior
--------------------+------------------------------------------------------------------------------------------------------------
Webhook idempotency | Repeated webhook event does not create duplicate payment records, orders, notifications, or loyalty points.
Amount verification | Webhook amount and currency must match the order payment due amount.
Manual override     | Any admin payment correction requires super_admin permission and audit reason.

6.8 Orders and Tracking
Order number format should be human-readable, such as SF-YYYYMMDD-001, and unique.
Order statuses: pending_payment, paid, processing, shipped, delivered, cancelled, payment_failed, refunded.
UI labels can map to simpler labels: Pending, Processing, Shipped, Delivered, Cancelled.
Store line items, customer snapshot, address snapshot, financial summary, shipping method, payment info, tracking number, and status history.
Admin can update order status and tracking number. Customer can track via dashboard or public tracking page.
Admin can print invoice from the order detail view. Invoice should use immutable order snapshots.

Acceptance scenario | Expected backend behavior
--------------------+-----------------------------------------------------------------------------------------------------------
Status transition   | Delivered order cannot move back to pending without super_admin override.
Tracking            | When tracking number is saved, customer notification is created.
Cancel order        | Cancelling a paid order must trigger payment refund workflow or mark refund_required, depending on policy.

6.9 Reviews and Ratings
Customers can write product reviews, ideally only after purchasing the product.
Reviews include rating, title/body, optional media, product, customer, order item reference, status, and admin reply.
Admin can approve, reject, hide, reply, or flag a review.
Product rating summary should update asynchronously after review changes.

Acceptance scenario | Expected backend behavior
--------------------+---------------------------------------------------------------------
Eligibility         | Customer cannot review the same purchased order item more than once.
Moderation          | Rejected or hidden reviews do not affect product average rating.

6.10 Loyalty and Referrals
Customer dashboard shows loyalty points balance, history, and reward actions.
Points ledger records source, delta, balance after, related order or referral, expiry, and status.
Referral dashboard shows referral code/link, invited users, conversion status, and rewards earned.
Referral reward should only become confirmed after referred customer completes qualifying action such as first paid order.

Acceptance scenario | Expected backend behavior
--------------------+---------------------------------------------------------------------------------------------
Ledger integrity    | Points balance is derived from transactions, not manually edited directly.
Fraud control       | Self-referral, duplicate device abuse, and repeated same payment identity should be flagged.

6.11 Notifications and Emails
Customer notifications: order placed, payment success/failure, shipped, delivered, coupon, loyalty, referral, review reply.
Admin notifications: new order, low stock, payment issue, new review, order cancelled, support/chat message.
Notification dropdown shows recent events and unread state.
Email templates for verification, reset password, order confirmation, shipping update, delivery confirmation, and admin alerts.

Acceptance scenario | Expected backend behavior
--------------------+--------------------------------------------------------------------------------------
Unread state        | Opening notification list does not automatically mark all as read unless UX confirms.
Delivery retry      | Failed email jobs retry with backoff and final failure is logged.

6.12 CMS, Settings, and Storefront Content
Admin can manage content banners, home popups, featured sections, homepage category blocks, footer contact info, and social links.
Settings include store profile, payment method availability, shipping methods, notification rules, and security/password settings.
CMS content should support draft, scheduled, active, and archived states.

Acceptance scenario | Expected backend behavior
--------------------+----------------------------------------------------------------------
Content visibility  | Only active content within publish window appears on storefront.
Settings audit      | Payment, shipping, tax, and notification setting changes are audited.

7. Data Model and Database Requirements
Use Microsoft SQL Server as the primary transactional database. Use UNIQUEIDENTIFIER or BIGINT primary keys based on team standard, with separate human-readable references for orders, payments, coupons, and customers. Store all money values as integer minor units. Store timestamps in UTC using datetimeoffset where possible. Use soft delete where records may be referenced by historical orders. Add rowversion columns for entities that need optimistic concurrency, such as products, inventory, orders, coupons, and settings.

SQL Server and EF Core rules
Every EF Core migration must be reviewed before deployment, especially changes to money, inventory, payment, and order tables.
Create indexes for product slug, SKU, category_id, brand_id, status, created_at, order_number, payment_reference, customer_id, coupon_code, and all common dashboard filters.
Use foreign keys for core relationships. Avoid disabling constraints just to make imports easier.
Use decimal only for calculated display values when needed, but store money totals as integer minor units to avoid rounding bugs.
Use rowversion for optimistic concurrency on inventory, product pricing, coupon, order, and settings records.
Use SQL Server transaction isolation carefully for checkout. The goal is no overselling, no duplicate coupon redemption, and no duplicate payment processing.
Avoid stored procedures for normal CRUD in v1 unless the query is complex reporting or performance-critical. Keep business rules in C# services so tests stay clear.

9. Workflows and State Machines

9.1 Registration and email verification
Customer submits sign-up form.
Backend validates email, phone, password strength, and terms acceptance if present.
Backend creates inactive or active-unverified user based on policy.
Backend generates verification token/code with expiry and queues email.
Customer verifies email. Backend marks user email verified and invalidates token.
Customer can access dashboard features once authenticated and verified if verification is required.

9.2 Product creation
Admin opens Add New Product modal.
Backend receives product fields, SKU, price, stock, SEO, images, active and featured flags.
Backend validates SKU uniqueness, price, category, image type, and product status.
Backend creates product, default variant, media records, inventory item, audit log, and search index job.
Product appears on storefront only if status is active, category is active, and stock policy allows display.

9.3 Checkout and payment
Customer cart is validated against product status, stock, coupon, flash deal, tax, and shipping method.
Backend returns checkout quote with subtotal, discount, tax, shipping, and total.
Customer places order. Backend uses idempotency key and creates pending_payment order.
Backend reserves inventory, creates order items and payment record, then initializes Paystack transaction.
Customer completes Paystack checkout.
Paystack webhook hits backend. Backend verifies signature and amount, marks payment paid, updates order to paid or processing, confirms stock reservation, creates notifications, queues email, and awards points if configured.
If payment fails or expires, backend releases inventory reservation and marks payment failed.

9.4 Order lifecycle

pending_payment
-> payment_failed
-> paid
-> processing
-> shipped
-> delivered
-> cancelled
-> refunded

Rules:
- pending_payment can expire and release stock.
- paid can move to processing or cancelled depending on fulfillment policy.
- shipped cannot be cancelled by customer.
- delivered is terminal unless refund/return policy is added.
- every transition writes order_status_history.

9.5 Inventory reservation state

available stock = stock_on_hand - reserved_qty

Cart add:
- Does not reserve stock in v1 by default.

Order created pending_payment:
- Reserve stock for each order item.

Payment confirmed:
- Convert reservation into committed sale or deduct stock_on_hand.

Payment failed, expired, or order cancelled before fulfillment:
- Release reservation.

Admin stock adjustment:
- Must not set stock_on_hand below reserved_qty unless super_admin override with reason.

9.6 Review lifecycle

pending
-> approved
-> rejected
-> hidden

Rules:
- Customer creates review after purchase if review eligibility is enabled.
- New review defaults to pending unless auto-approve is enabled.
- Approved reviews update product average rating and review count.
- Hidden/rejected reviews do not count toward rating summary.

Reliability and scaling
All mutation endpoints use request_id logging and structured errors.
Checkout and payment endpoints support idempotency keys.
SQL Server transactions guard inventory and order creation.
Queues support retry with exponential backoff and dead letter handling.
Uploads use object storage, not local server disk.
Backups run daily for database and object storage metadata.
Use database migrations and rollback strategy for every release.
Use API versioning and OpenAPI documentation before frontend integration begins.

Accessibility and localization backend support
Product and media records include alt_text where images are exposed to customers.
Money formatting should be frontend-controlled, but backend sends currency and integer amount fields.
Phone numbers should be stored in E.164 where possible.
Dates should be returned in ISO 8601 UTC plus local display formatting handled by frontend.

M1 - Catalog and admin basics  | Products, categories, media, inventory, admin product/category screens, storefront catalog APIs. | Admin can create active product and customer storefront can view/search it.
M2 - Cart, checkout, payment   | Cart, quote, order creation, Paystack initialize/verify/webhook, inventory reservation.          | Customer can complete paid order end-to-end in sandbox.
M3 - Orders and operations     | Admin order detail, status updates, tracking, invoice, customer track order, notifications.      | Admin can fulfill an order and customer sees timeline changes.
M4 - Promotions and engagement | Coupons, flash deals, reviews, wishlist, loyalty, referrals.                                     | Marketing flows work and pricing rules are tested.
M5 - CMS, analytics, hardening | Content blocks, settings, dashboard rollups, security hardening, monitoring, backups.            | Admin dashboard works and release checklist passes.

Suggested implementation order
Start with database schema and OpenAPI contract before frontend wiring.
Build auth, roles, and admin audit logging early because every admin feature depends on them.
Build catalog and inventory before checkout because checkout cannot be correct without price and stock rules.
Build Paystack webhook processing before polishing checkout UI because payment truth is backend-side.
Add analytics rollups after transactional flows are stable, not before.
